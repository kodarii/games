  <files>apps/client/src/lib/queries.ts</files>

  <action>
    Dla każdego `useMutation` w `queries.ts` który wywołuje POST mutation function (`createGame`, `createWishlistItem`, `importData`, `uploadCover`, `moveToCollection`, IGDB save/delete):

    1. **Dodaj `useRef` per mutation hook** — `const idempotencyKeyRef = useRef(newIdempotencyKey())` (lub `crypto.randomUUID()` przez `newIdempotencyKey`). Ref jest stable across re-renders.
    2. **Pass do mutationFn** — `mutationFn: (input) => createGame(input, idempotencyKeyRef.current)`.
    3. **Reset po success** — w `onSuccess` callback: `idempotencyKeyRef.current = newIdempotencyKey()` (fresh key na następną mutation invocation; same instance tej samej mutation NIE generuje nowego key'a, bo to byłby new mutation).

    Przykład transformacji `useCreateGame`:
    ```ts
    // BEFORE
    export function useCreateGame() {
      const qc = useQueryClient();
      return useMutation({
        mutationFn: createGame,
        onSuccess: () => qc.invalidateQueries({ queryKey: ['games'] }),
      });
    }

    // AFTER
    export function useCreateGame() {
      const qc = useQueryClient();
      const idempotencyKeyRef = useRef(newIdempotencyKey());
      return useMutation({
        mutationFn: (input: CreateGameInput) => createGame(input, idempotencyKeyRef.current),
        onSuccess: () => {
          idempotencyKeyRef.current = newIdempotencyKey();
          qc.invalidateQueries({ queryKey: ['games'] });
        },
      });
    }
    ```

    **Why this fixes T-04-21:**
    - **Within same component instance:** ref stays stable, retry (RQ `retry: 1`) replays mutationFn → SAME key → server dedupli ✓.
    - **After window.location.assign('/'):** new page load → new component instance → new ref → new key — to JEST poprawne, bo user świadomie zdecydował się retry'ować po reset, server traktuje to jako new mutation. Wcześniejsza próba (jeśli server przetworzył) zostawiła cached response pod OLD key, ale klient nie ma już dostępu do niego — server cache expire'uje sam (`IDEMPOTENCY_TTL_HOURS` default 24h). Klient widzi dodatkowy duplicate **tylko jeśli** server processed original request przed reset; dla single-user app to akceptowalne (user widzi duplicate, usuwa go).

    **Zakazy:**
    - NIE dodawaj `useRef` do GET queries (`useQuery`) — idempotency-key nie ma sensu dla GETs.
    - NIE rób global idempotency-key cache (np. w localStorage) — komplikuje invalidation logic; per-component useRef wystarcza dla retry scenariuszy.
    - NIE pomijaj reset w `onSuccess` — bez reset, kolejne kliknięcie "Create game" przy tym samym component instance użyłoby tego samego key → server dedupli → user widzi cached response zamiast new game.
    - NIE pomijaj reset w `onError` (opcjonalne — jeśli error jest server-side, retry powinien użyć SAME key żeby dedupli; jeśli error jest client-side validation, key reset jest niepotrzebny — zostaw bez reset w onError).
  </action>
