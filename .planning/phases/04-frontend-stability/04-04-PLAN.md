    **Pattern (per hook):**
    1. **Import:** dodaj `useRef` z `'react'` (jeśli nie jest już) + `newIdempotencyKey` z `'./api'`.
    2. **useRef cache:** `const idempotencyKeyRef = useRef(newIdempotencyKey())` — stable across re-renders per mutation instance.
    3. **Pass do mutationFn:** wywołaj refactored api function z `idempotencyKeyRef.current` jako trailing arg.

      ```ts
      onSuccess: () => qc.invalidateQueries({ queryKey: ['games'] }),

      // AFTER
      const idempotencyKeyRef = useRef(newIdempotencyKey());
      // ...
      mutationFn: (input: CreateWishlistInput) =>
        createWishlistItem(input, idempotencyKeyRef.current),
      onSuccess: () => {
        idempotencyKeyRef.current = newIdempotencyKey();
        qc.invalidateQueries({ queryKey: ['games'] });
      },
      ```

    - **`useCreateGameMutation`** (linia ~107) — analogicznie do useCreateWishlistMutation.

    - **`useUploadCoverMutation`** (linia ~228) — **NIE ma `onSuccess`** (verified — single-property hook z tylko `mutationFn`). MUSISZ dodać `onSuccess` żeby reset key:
      ```ts
      // BEFORE
      return useMutation({
        mutationFn: (file: File) => uploadCover(file),
      });

      // AFTER
      const idempotencyKeyRef = useRef(newIdempotencyKey());
      return useMutation({
        mutationFn: (file: File) => uploadCover(file, idempotencyKeyRef.current),
        onSuccess: () => {
          idempotencyKeyRef.current = newIdempotencyKey();
        },
      });
      ```

    - **`useMoveToCollectionMutation`** (linia ~235) — używa `onMutate`/`onError`/`onSettled` (optimistic update z rollback), NIE ma `onSuccess`. MUSISZ dodać osobny `onSuccess` żeby reset key:
      ```ts
      // BEFORE: { mutationFn, onMutate, onError, onSettled }
      // AFTER: { mutationFn (with idempotencyKeyRef.current), onMutate, onError, onSuccess (NEW — only resets key), onSettled }
      // - onSuccess: () => { idempotencyKeyRef.current = newIdempotencyKey(); }
      // - onSettled pozostawić bez zmian (nie ruszać invalidate logic)
      ```
      **Krytyczne:** reset key MUSI być w `onSuccess` (nie w `onSettled`), żeby retry-after-error wciąż używał tego samego key'a. Reset w `onSettled` złamałby semantykę "retry-after-fail uses same key".

    **Why this fixes T-04-21:**
    - **Within same component instance:** ref stays stable, RQ `retry: 1` replays mutationFn → SAME key → server dedupli (returns cached 2xx response) ✓.
    - **After `window.location.assign('/')`:** new page load → new component instance → new ref → new key — to JEST poprawne, bo user świadomie zdecydował się retry'ować po reset; server traktuje to jako new mutation. Wcześniejsza próba (jeśli server processed) zostawiła cached response pod OLD key, ale klient nie ma już dostępu do niego (24h TTL na server side cleanup). Klient widzi dodatkowy duplicate **tylko jeśli** server processed original request przed reset.

    **Zakazy:**
    - NIE dodawaj `useRef` do GET queries (`useQuery`) — idempotency-key nie ma sensu dla GETs.
    - NIE rób global idempotency-key cache (np. w localStorage) — komplikuje invalidation logic; per-component useRef wystarcza dla retry scenariuszy.
    - NIE pomijaj reset w `onSuccess` — bez reset, kolejne kliknięcie ("Create game" po pierwszym sukcesie) użyłoby tego samego key → server zwróci cached response zamiast new game.
    - NIE resetuj klucza w `onError` — retry tej samej operacji MUSI użyć tego samego key (główny powód istnienia tego refactoru). Reset w error byłby antypatternem.
    - NIE resetuj klucza w `onSettled` — `onSettled` odpala się PO `onError` też → equivalent reset-on-error. Same problem.
    - NIE rób inline `crypto.randomUUID()` — używaj `newIdempotencyKey()` z `./api`.

**Granice ochrony (honest framing):**
- ✅ TanStack Query `retry: 1` after network failure → same key → server dedupli.

- ❌ Server commits DB but crashes pre-response-serialize → retry recreates (T-04-28 — acceptable rare edge).

Out of Scope:
- localStorage / sessionStorage caching idempotency-key across page reloads — over-engineered for single-user, server cache expires after sweep cycle (24h hard bound) anyway.
- `updateGame` PUT (api.ts:81) and `deleteGame` DELETE (api.ts:84) — these don't currently use idempotency-key; this plan does NOT add it (optimistic-lock + HTTP idempotency are sufficient per T-04-21 analysis).

Dodanie idempotency-key do PATCH wymagałoby też zmiany server-side handler logic; out of scope dla Phase 04. Track jako potential FE-V2 jeśli problem ujawni się produkcyjnie.
- Server-side advisory lock (SELECT FOR UPDATE na idempotency-key) dla cleaner concurrent race handling — nadmiarowe dla single-user; client-side `disabled-while-pending` wystarcza.
- importData useRef caching (Task 2c decision) — single-shot admin UX, no retry semantics needed.
