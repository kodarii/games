### Q6 — F-08-3: round-trip test bypassed ImportData.execute

**Status: OPEN — BLOCKER. The fix introduces a different bug: the test code as written cannot compile against the real `ImportData` API.**

Evidence — three signature mismatches in `05-08-PLAN.md` Task 3:

**Mismatch 1 (Step 2, line 482):**
- Plan: `const importData = new ImportData(repo);`
- Actual (`apps/api/src/application/import/import-data.ts:22-28`): `constructor(gameRepo: GameRepository, platformRepo: PlatformRepository, importRepo: ImportRepository, idGenerator?)`. Three required deps, plan passes one. TS error.

**Mismatch 2 (Step 3, line 508):**
- Plan: `await importData.execute({ snapshot: snapshot1, mode: 'replace', userId: TEST_USER_A })`
- Actual signature (`import-data.ts:30-34`): `execute(userId: string, rawJson: string, mode: ImportMode)`. Positional, not object-bag; expects `rawJson` as a JSON string, not a snapshot object.
- Implication: the test must `JSON.stringify(snapshot1)` and pass it as `rawJson`. The call site would be `await importData.execute(TEST_USER_A, JSON.stringify(snapshot1), 'replace')`.

**Mismatch 3 (Step 2 — no DI for gameRepo/platformRepo):**
- `ImportData` needs `GameRepository` and `PlatformRepository` because:
  - `import-data.ts:66`: `await this.platformRepo.list(userId)` (merge mode resolves platform-name collisions).
  - The gameRepo isn't called in `execute()` directly (only the importRepo gets called for the merge/replace), but it's a constructor param — still required.
- The test must instantiate Drizzle repos for these — `new DrizzlePlatformRepository(db)` if such exists, similar for games. If those repos don't yet support the Q7 DI pattern (verified: `05-03-PLAN.md` only refactors `DrizzleImportRepository`'s constructor), the test cannot inject the in-memory DB into them; they'll hit the production singleton `db` from `db/client.ts` — which means the test exercises a mix of in-memory + production DB. That's worse than the F-08-3 status quo.

**Mismatch 4 (idGenerator semantics):**
- `parseImport` (called inside `execute`) calls `idGenerator()` for every game/platform to generate "fresh" IDs at parse time. The default is `crypto.randomUUID()`. So a snapshot with externalIds `'g-1'`...`'g-3'` becomes a `NewGame[]` with 3 random UUID externalIds. The round-trip then writes those random UUIDs into the DB. Re-export reads back random UUIDs. The diff `stripVolatile(snapshot2).toEqual(stripVolatile(snapshot1))` compares externalIds — and they won't match.
- Actually re-reading `import-data.ts:119`: `NewGame.create({...}, () => g.externalId)` — the idGenerator IS passed as `g.externalId` for each game. So the externalIds DO survive parseImport. Good. But the test must NOT override idGenerator with `crypto.randomUUID()`, or it breaks.

Combined: as written, Task 3's code snippet WILL NOT COMPILE and WILL NOT EXECUTE. The intent is correct (route round-trip through the production use-case), but the spec is wrong. A subagent executing this plan literally will fail to produce working code.

**Recommended action:** REWORK Task 3 to:
1. Construct `ImportData` with all three deps wired against the in-memory DB. This either requires (a) extending Q7 DI to `DrizzleGameRepository` + `DrizzlePlatformRepository`, or (b) checking whether those repos can already accept an injected `db`.
2. Adjust calls to `importData.execute(userId, JSON.stringify(snapshot), mode)`.
3. Verify the diff comparison still works when externalIds round-trip (per `import-data.ts:119`, they do).
