<objective>
Wyciągnąć migracje DB z boot-path API do versioned `scripts/deploy.sh` wykonywanego ahead-of-restart na VPS. `client.ts` zachowuje auto-migrate tylko dla dev (`NODE_ENV !== 'production'`).

Purpose: Eliminuje boot-time race (proces nie wstaje dopóki migracja w toku); `set -euo pipefail` + `trap restore_and_exit ERR` zapewniają, że bad migracja zatrzymuje deploy PRZED restartem ORAZ przywraca DB ze snapshotu zrobionego tuż przed migracją → stary proces zostaje przy życiu na starym kodzie + **przywróconej** starej DB (bez ryzyka pół-zmigrowanego schematu, który by powodował 500-tki). VACUUM INTO + trap = enterprise-grade rollback przy zerowym narzucie operacyjnym.

**Q2 świadomy trade-off:** Tracimy zapisy zrobione *między* zrobieniem snapshotu a fail migracji (deploy trwa kilkanaście sekund, single-user, akceptowalne). Retention 10 backupów daje audytowalną historię.

**Mikrus production invariants (od Q3 grilla):** Nowy versioned `scripts/deploy.sh` MUSI zachować trzy invariants istniejącego produkcyjnego skryptu na Mikrusie, inaczej slice 05-01 jest regresją deployu zamiast correctness fix-em:
  1. `export PATH="/root/.bun/bin:$PATH"` na początku — bez tego appleboy/ssh-action dostaje `bun: command not found` (non-interactive SSH nie ładuje .bashrc).
  2. `bunx vite build` (czysty Vite, BEZ `tsc -b`) — Mikrus ma 1 GB RAM, pełny TypeScript build wiesza VPS-a.
  3. `bun install` BEZ `--frozen-lockfile` — historyczne konflikty drizzle-kit/better-sqlite3 podczas initial setup-u. Verification po pierwszym deployu decyduje czy zaostrzyć.

**Q4 hardening (rollback correctness):** Pierwsza wersja planu zakładała, że `apex-api` żyje przez całe okno backup→migrate→trap-restore. To okazało się fundamentalnie niebezpieczne na SQLite WAL: (a) snapshot przez `VACUUM INTO` na readonly handle nie gwarantuje spójności WAL frames niecheckpointowanych; (b) `cp BACKUP_FILE apex.db` truncuje **ten sam inode** który żywy proces trzyma otwarty → SHORT_READ / CORRUPT podczas reading; (c) `rm apex.db-wal` przy żywym fd → orphan WAL, dane commitsowane przez żywy proces przepadają cicho. SC-1 ROADMAP-u byłoby spełnione optycznie, nie materialnie. Wariant A:
  - `$SYSTEMCTL_CMD stop apex-api` PRZED backupem (żaden writer aktywny przez całe okno snapshot+migrate+restore). Q6: injection point z prod default `sudo systemctl`.
  - `PRAGMA wal_checkpoint(TRUNCATE)` w `backup.ts` przed `VACUUM INTO` — gwarantuje że wszystkie WAL frames są w głównym DB file zanim snapshot zostanie zrobiony.
  - `$SYSTEMCTL_CMD start apex-api` PO migrate (happy path) ORAZ w trapie (fail path, na zrestored DB).
  - **Git-ref rollback w trapie:** wrapper VPS przekazuje `DEPLOY_ROLLBACK_REF=$(git rev-parse HEAD)` PRZED `git pull`. Trap robi `git reset --hard "${DEPLOY_ROLLBACK_REF}"` aby stary kod uruchomił się na zrestored starej schemie (inaczej nowy kod + stara DB = 500-tki).
  - `mv apps/client/dist apps/client/dist.prev` przed nowym build-em. Trap robi `rm -rf dist && mv dist.prev dist` — przywraca stary build instant, bez rebuildu (rebuild po git reset wymagałby Vite build pod OOM-em Mikrusa).
  - Trade-off: ~10–15s downtime na happy path zamiast ~3s. Akceptowalne dla single-user trackera. Zysk: materialna spójność kod+schema+dist po failed deployu.

**Q6 (lokalna testowalność trap-path):** Trap rollback to najbardziej krytyczna ścieżka w pipeline — odpala się tylko gdy migracja się wywali, i musi zadziałać za pierwszym razem na prod. Naive mock `function systemctl(){...}; export -f systemctl` NIE działa: (a) `sudo` ma `env_reset` + `secure_path` w sudoers → wycina BASH_FUNC_*%% przed execve targetu; (b) `sudo systemctl` to execve binary, nie shell command — bash function nigdy nie zostanie zobaczona; (c) developer i tak nie ma passwordless sudo lokalnie → skrypt zawisi na promcie. Rozwiązanie: jeden env var `SYSTEMCTL_CMD="${SYSTEMCTL_CMD:-sudo systemctl}"`, wszystkie wywołania zamienione na `$SYSTEMCTL_CMD stop/start apex-api`. Production default identyczne (`sudo systemctl`); lokalnie `SYSTEMCTL_CMD="echo [mock] systemctl" bash scripts/deploy.sh` przeprowadza trap end-to-end bez sudo. Bonus: `SYSTEMCTL_CMD="false"` symuluje failure systemctl → trap fires, można zweryfikować, że stop-failure też triggeruje rollback. Wzorzec identyczny do istniejącego `APP_DIR_REPO="${APP_DIR_REPO:-...}"` — zero nowej koncepcji.

    import { Database } from 'bun:sqlite';
    import { resolve } from 'node:path';

    const target = process.argv[2];
    if (!target) {
      console.error('usage: db:backup <target-path>');
      process.exit(1);
    }

    const sourcePath = resolve(import.meta.dir, '..', 'data', 'apex.db');
    // Read/write open — wymagane do PRAGMA wal_checkpoint(TRUNCATE).
    // Caller (scripts/deploy.sh) zatrzymuje apex-api przed wywołaniem, więc nie ma
